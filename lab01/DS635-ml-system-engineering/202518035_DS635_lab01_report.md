# Part 2 — Cache Detective

For N=1024, each matrix contains: $$1024^2$$
 float32 elements. Since each float32 occupies 4 bytes, one matrix occupies approximately 4 MiB.

A 64-byte cache line contains: $$64/4=16$$ float32 values.

## Predicted vs Measured D1 Misses

### D1 Miss Prediction

A 64-byte cache line holds 16 float32 values because each float32 is 4 bytes.

For the naive `i-j-k` ordering, A is accessed row-wise, but B is accessed column-wise. Since consecutive B elements are separated by an entire row, almost every B access causes a D1 miss. Therefore, the dominant miss count is approximately:

$$
M_{\text{naive}} \approx N^3
$$

For the reordered `i-k-j` version, both B and C are accessed row-wise as `j` increases. Each cache line supplies 16 consecutive float32 values, so the dominant miss count is approximately:

$$
M_{\text{reordered}} \approx \frac{N^3}{16}
$$

For \(N=1024\):

$$
N^3 = 1,073,741,824
$$

and

$$
\frac{N^3}{16}=67,108,864
$$

These are the predicted values shown in the table below.

| Version   | Predicted D1 misses | Measured D1 misses | Measured / Predicted |
| --------- | ------------------: | -----------------: | -------------------: |
| Naive     |       1,073,741,824 |      1,076,180,813 |              1.0023× |
| Reordered |          67,108,864 |         67,439,438 |              1.0049× |

The predictions are very close to the measurements.

## Cachegrind Results

### Naive

```text
D1 misses:       1,076,180,813
D1 read misses:  1,075,066,259
D1 miss rate:    49.9%
LLd misses:      263,948
```

### Reordered

```text
D1 misses:       67,439,438
D1 read misses:  67,373,464
D1 miss rate:    2.1%
LLd misses:      263,949
```

## Q2.1

In the naive i-j-k ordering, A is accessed across a row, giving good spatial locality because one 64-byte cache line contains 16 float32 values. B is accessed down a column, so consecutive accesses are far apart in memory and usually require different cache lines. Since there are two reads per iteration and approximately one of them, B, misses, the overall read miss rate is close to 50%.

## Q2.2

The LLd misses were almost identical: 263,948 for the naive version and 263,949 for the reordered version. LLd misses indicate that data was not found in the last-level cache and therefore had to be obtained from lower in the memory hierarchy. The large reduction in D1 misses, from about 1.076 billion to 67.4 million, while LLd misses stayed almost unchanged shows that the speedup came primarily from better locality in the upper cache hierarchy rather than from reducing accesses to main memory.

# Part 3 — Find My Memory Wall

My CPU has a 16 MiB L3 cache.

The assignment predicts the wall using the size of matrix B: $$ 4N^2 = L3 $$

Therefore:

$$ 4N^2 = 16 \times 1024^2 $$

giving:

$$ N^* = 2048 $$

Thus my predicted threshold was **N*=2048**.

## SIMD Sweep

|    N | GFLOP/s |
| ---: | ------: |
|  512 |   20.97 |
| 1024 |   17.43 |
| 1536 |   13.07 |
| 2048 |   11.72 |
| 3072 |    9.91 |
| 4096 |    8.92 |

## Q3.1

My first estimate considered only matrix B. Since B occupies \(4N^2\) bytes and my L3 cache is 16 MiB:

$$
4N^2 = 16\times2^{20}
$$

giving \(N=2048\).

However, the computation actually uses three \(N\times N\) float32 matrices: A, B and C. Considering all three:

\[
3(4N^2)=16\times2^{20}
\]

which gives \(N\approx683\).

The measured GFLOP/s decreased gradually as N increased: 20.97 at N=512, 17.43 at N=1024, 13.07 at N=1536, and 11.72 at N=2048. Therefore, there is no single sharp cliff at either predicted value. The gradual decline makes sense because cache capacity is shared with multiple matrices and other data, and performance is affected progressively as the working set becomes larger than the faster cache levels.

## Q3.2

As N increased, the sizes of A, B and C and therefore the total working set increased, causing more of the active data to exceed the capacity of the faster cache levels and resulting in more expensive memory-hierarchy accesses and lower GFLOP/s.

# Part 4 — Tiling

For tiling, the approximate working set is:

$$
3T^2 \times 4\text{ bytes}
$$

The three T×T tiles correspond approximately to tiles of A, B and C.

My CPU has:

```text
L1d: 32 KiB per core
L2:  1 MiB per core
L3:  16 MiB shared
```

The L1d and L2 values are per-core because the reported 192 KiB L1d and 6 MiB L2 are six separate cache instances.

## Tile Sweep

|   T | Working set | GFLOP/s |
| --: | ----------: | ------: |
|  32 |      12 KiB |    2.22 |
|  64 |      48 KiB |    7.09 |
| 128 |     192 KiB |   11.88 |
| 256 |     768 KiB |   17.06 |

My initial prediction was T=128 because it provides more reuse than smaller tiles while still fitting comfortably inside the 1 MiB per-core L2. The measurement showed that T=256 performed best.

## Q4.1

Increasing the tile size increased data reuse, so more computation could be performed on data already present in the cache and fewer expensive lower-level memory accesses were needed. T=256 did not fall off because its approximately 768 KiB working set still fits within the 1 MiB per-core L2 cache. Although it does not fit in the 32 KiB L1d cache, the additional reuse from the larger tile outweighed this cost, giving 17.06 GFLOP/s compared with 11.88 GFLOP/s for T=128.

## Bounds Check Experiment

The original inner loop was:

```c
for (int j = jj; j < jj + T; j++)
```

It was changed to:

```c
for (int j = jj; j < jj + T && j < n; j++)
```

For N=2048 and T=256:

$$
2048 \bmod 256 = 0
$$

so the additional `j < n` condition is semantically unnecessary.

### Before Guard

```text
GFLOP/s: 17.76
ymm count: 10
```

### After Guard

```text
GFLOP/s: 3.36
ymm count: 10
```

The performance decreased by approximately:

$$
17.76/3.36 \approx 5.29\times
$$

Both versions still passed the correctness check.

## Q4.2

Adding the semantically unnecessary bounds check reduced performance from 17.76 GFLOP/s to 3.36 GFLOP/s, a slowdown of approximately 5.3×. The compiler must reason about the additional loop termination condition and prove that vectorized loads and stores remain within valid bounds for multiple iterations. On my GCC build, the simple `grep -c ymm` count remained 10 before and after the guard, so the global `ymm` count did not provide evidence of a change in vector instruction count; nevertheless, the large performance difference shows that the additional condition substantially affected the generated optimization.

# Part 5 — All Cores

My machine has:

```text
6 physical cores
12 logical CPUs
```

Before running the experiment, I predicted approximately 5× speedup at 12
threads. My CPU has 6 physical cores and 12 logical CPUs, so the 12 threads
do not correspond to 12 independent physical cores. I therefore expected
the speedup to be substantially below the ideal 12× because the two hardware
threads on each physical core share the core's resources.

## OpenMP Scaling

| ------: | ------: | ------------------: |
|       1 |   13.84 |               1.00× |
|       2 |   24.81 |               1.79× |

|      12 |   72.28 |               5.22× |

The measured 12-thread speedup was therefore approximately **5.22×**, close to the predicted 5×.

## Q5.1

The three main factors limiting scaling are the physical-core/SMT limitation, the CPU power and thermal budget, and shared resources such as the L3 cache and DRAM bandwidth. My CPU has 6 physical cores but 12 logical CPUs, so the additional SMT threads do not provide another complete physical core with independent execution resources. The strongest evidence is the 8-to-12-thread result: performance increased only from 70.70 to 72.28 GFLOP/s, or about 1.02×, showing that the available physical and shared resources were already close to saturation.

# Summary

The experiment showed that matrix multiplication performance is affected by several layers of the system:

1. **Implementation level:** NumPy and compiled C greatly change the performance characteristics compared with naive Python.
2. **Memory access pattern:** Loop reordering dramatically improves cache locality and reduced D1 misses from approximately 1.076 billion to 67.4 million.
3. **Cache capacity:** Increasing N eventually makes the working set exceed the capacity of faster cache levels, reducing SIMD throughput.
4. **Tiling:** Blocking increases reuse and can improve performance when the active tile working set fits in an appropriate cache level.
5. **Compiler optimization:** A seemingly unnecessary bounds check can substantially affect optimization and measured performance.
6. **Parallelism:** OpenMP provides substantial scaling, but performance eventually saturates because the number of logical CPUs does not correspond to the same number of independent physical execution resources and because shared resources become bottlenecks.

The best OpenMP result measured in the main ladder was **54.77 GFLOP/s**, while the separate 12-thread scaling experiment with T=256 reached **72.28 GFLOP/s**.
